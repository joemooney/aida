Under `--no-human=both`, when the orchestrator detects a punt it spawns a **fresh `claude -p` process** with the `/aida-advise` skill. That process boots cold: it loads the persistent substrate (memory pack, CLAUDE.md, discipline docs, spec graph, relevant plan files), renders a verdict, exits. It is NOT in conversation with any live advisor session you may also be running. The two share only what is written to disk.

**Why:** This is the load-bearing fact behind most substrate-discipline memories. A cold-boot advisor is *only as good as what it can load*. In-flight judgment that lives in a running advisor session — design decisions made conversationally, framings still half-formed, the texture of "the room" — never reaches the headless advisor unless externalized into memories, spec comments, acceptance criteria, or plan files. The headless advisor and a live one are the same Claude *model* with different *context*; the gap is closeable by enriching the substrate, not by waiting for a smarter model.

**Virtue to preserve, not limitation to overcome:** The cold-boot model has no daemon to start, crash, leak memory, hold a stale lock, or version-skew against. Every invocation is deterministic in its inputs (substrate on disk + punt context) and reproducible. For a single-developer tool that is a *huge* operational win — no "is the advisor daemon up?" failure mode because there is no daemon. Whatever richer advisor architecture lands later, **cold-boot stays the always-available fallback**, not a deprecated path. The simpler thing earns its keep by always working when the fancy thing is misbehaving.

**How to apply:**
- Treat every memory write, doc seed, and refinement-to-acceptance edit as **training data for the cold-boot advisor**. Not a metaphor — literally what gets loaded at `claude -p` startup.
- When you find yourself making a live judgment call you would want the headless advisor to make the same way, externalize it — memory if generic, spec comment if scoped to one spec, acceptance criterion if binding on the implementer. See [[feedback_explicit_paste_ready_prompts]], [[feedback_refinements_must_be_acceptance_criteria]].
- Do NOT assume a running drain has any of *this* conversation's context. When triaging a NeedsAttention punt in the morning, the punt comment + spec acceptance is *all* the advisor had to work with.
- Watch the structural ceiling: even a fully-substrate-rich headless advisor cannot replicate a live session's in-flight judgment. **Three trajectories** for closing the gap, in increasing operational cost:
  1. **Substrate enrichment** (what every memory write feeds). The headless advisor and a live one converge as the substrate grows. Compounding, no architectural change required. Always running.
  2. **Fork-from-live-session** (SPIKE-11 validated viable 2026-05-20; **implemented STORY-360, 2026-05-21**). When a live advisor session is registered (`aida advisor register`), the orchestrator copies its JSONL transcript into the spec's worktree project slug under a new UUID and `claude --resume <fork> -p "<punt>"`. The fork boots with the live session's full conversation context, renders a verdict one-shot, terminates. No daemon; uses Claude Code primitives. Falls back to cold-boot when no live session is registered, the registered session looks dead, the transcript exceeds `[advisor] max_source_size_mb`, or `fork_mode = "never"`. Measured: 6.7s latency, ~$4.25 first fork (cache-creation tax), ~$0.03 within 5-min cache TTL; source isolation byte-clean; project-slug agnostic. Wired into `aida-cli/src/auto_complete.rs::run_advisor` via `aida-cli/src/advisor.rs::plan_fork`. See `docs/spikes/2026-05-20-spike-11-session-forking.md` and the **Fork-from-live** section of `docs/autonomous-drain.md`.
  3. **Persistent advisor entity** (SPIKE-10 / MCP-bus / daemon). A long-lived process that accumulates context across drains. Solves the gap most completely but introduces real ops burden (server lifecycle, version skew, crash recovery, concurrency). Not validated as the right shape — explore (2) first.
