### Conclusion on order

Nothing depends on Git's exact Kahn order. Beyond human display, the order
feeds three semantic decisions (shipped anchor, `shipped_pr`, branch-search
prefix). All three want "newest referencing commit", which is the stated
contract of the field (`trace.rs:630`). They do not depend on how `--date-order`
breaks ties.

Measured on this repo: committer-date skew is zero. Of 83,827 commits, 0 have a
parent with a later committer date. 4,010 have a parent in the same second.
For 12 sampled ids (BUG-2221, BUG-2224, STORY-1889, TASK-2347, STORY-82,
BUG-1993, BUG-1594, STORY-1649, BUG-546, TASK-241, STORY-634, BUG-1528), Git's
`--date-order` output is non-increasing in committer date in every case.
"ct desc, OID asc" reproduced it exactly for 7 ids. The 5 that differed differ
only inside same-second groups. Without skew, `--date-order` is a committer-date
sort; only the tie order is Git-internal.

Recommendation: accept **O2**, with a tie-break that is topologically safe:
**committer time desc, then index batch desc, then position within the batch
asc**. Each batch is walked with `--date-order` (see 2.3), so a parent never
sorts ahead of its same-second child. Inside a single batch the order equals
Git's. Under committer-date skew (none here today), O2 puts the latest-dated
commit first, which matches the "newest" contract better than Kahn order does.
The shipped anchor is the commit with the latest date, not the topologically
first one. Withdrawing the 23:55 O2 rejection is the advisor's call. This is
the evidence.

## 2. Design: incremental append-only spec-id -> commit index

Scope: the `aida show` deadline path only (`collect_git_linkage_until`,
`trace.rs:984`, reached from `print_git_linkage` and the show JSON). Non-show
callers keep the original query unchanged, as with every earlier slice.

### 2.1 Storage

`$(git rev-parse --git-common-dir)/aida/linkage-index/v1/`, so linked worktrees
share it. A seat clone has its own common dir and its git calls go through the
same clone-safe helper as the original query. A refusal there is "unknown",
exactly as today.

- `meta`: format version, `PARSER_VERSION` (a constant bumped whenever
  `extract_spec_ids_from_commit` / `extract_referenced_spec_ids_from_commit` /
  `extract_trace_line_spec_ids` change, guarded by a ratchet test that hashes
  their source), object format, and the `i18n.commitEncoding` /
  `i18n.logOutputEncoding` values. Any mismatch means rebuild.
- `frontier`: the tip set (`rev-list --all --no-walk` output) as of the last
  completed batch, plus the batch counter. Written via temp + fsync + rename,
  and only after the batch's shard appends are fsynced.
- `shards/<xx>`: 256 append-only files keyed by a hash of the upper-cased spec
  id. One line per (commit, resolved id):
  `oid ct batch pos ID literal-variants`. `literal-variants` lists the exact-case
  spellings of the id found in the message. A query for `X` matches only when
  `X` is among them, which reproduces the case-sensitive `-F --grep` filter that
  runs ahead of the case-insensitive resolver. Lines without a trailing newline
  (torn append) are ignored.
- Size, measured: 61,507 commits carry an id-like token, 72,297 (commit, id)
  pairs, about 4-5 MB total, about 20 KB per shard.

Subjects and short SHAs are NOT stored. `%h` length grows with the repo, so
both are read at query time from Git (2.4).

### 2.2 Query (warm)

1. T0 = `git rev-list --all --no-walk`: the tip set with exactly `--all`'s
   semantics, including other worktrees' HEADs. It is read ONCE, and every later
   step uses T0 explicitly (never `--all` again), so the answer is for one
   consistent ref state, as the original's single ref read is.
2. If T0 differs from `frontier`, run an incremental walk (2.3).
3. Read the shard(s) for the wanted ids (display, agreed, origin), filter by
   literal-variant, and dedupe by oid (keep the first occurrence's
   batch/pos).
4. Reachability: one `git rev-list --stdin` fed `<hits>` + `^<T0 tips>`. A hit
   that appears in the output is unreachable from T0 (for example, its branch
   was deleted unmerged) and is dropped. This replaces ref-set equality, so ref
   churn never invalidates the index.
5. Metadata: one `git log --no-walk --stdin --format=%H%x1f%h%x1f%s` over the
   surviving hits.
6. Sort by O2 and hand `commits` to the unchanged downstream code (shipped
   check, branch search, renderers).

### 2.3 Incremental update

`git log --date-order --stdin --format=%H%x1f%ct%x1f%B%x1e` fed
`<T0 tips not in frontier>` + `^<frontier tips>`. Only the changed tips go in as
positives: unchanged tips are already covered, and passing `--all` cost 70-83 ms
against 25-56 ms (measured below). Each record runs through the same BUG-546
resolver used at `trace.rs:1209-1214`. Records with resolved ids are appended
with the next batch number and their walk position. Then `frontier := T0`.

Old tips that disappear from T0 simply leave the frontier. The commits they
contributed stay in the index and are filtered by step 4. A deleted ref that
reappears gets re-walked, and the duplicate rows are deduped on read. When the
line count exceeds twice the unique count, the shards are compacted under the
lock (rewrite + rename).

Writers take `lock` with O_EXCL. If the lock is held, the reader walks the same
batch in memory, answers from it, and writes nothing.

### 2.4 Cold start and rebuild

There is no separate build cost on the show path. A cold key runs ONE
`git log --all --date-order --format=%H%x1f%ct%x1f%B%x1e` (725 ms measured,
versus 650 ms for the original grep query), answers the query in-process
through the same resolver and literal check, and writes the index from the same
output. If that walk misses its budget, the result is the existing
"incomplete" outcome, exactly as the original query's timeout is today.

### 2.5 Fail closed

Each of these runs the ORIGINAL `--date-order --grep` query unchanged (and
schedules a rebuild where noted):

- `meta` is missing, unreadable, or mismatched (rebuild)
- shallow repo (`shallow` file present) or any `refs/replace/*` or grafts: the
  index is disabled
- any git error in steps 1-5, including a frontier or hit object pruned by gc
  (rebuild)
- the update or reachability call exceeds its share of
  `LINKAGE_COMMIT_LOG_TIMEOUT` clipped to the deadline (whatever budget remains
  goes to the original; if none remains, the result is "incomplete")
- a shard line fails to parse (rebuild)

No budget, deadline, cutoff, or telemetry change. The negative proof
(`show_negative.rs`) stays in front, unchanged. A `PositiveHit` / `RunOriginal`
outcome goes to the index instead of straight to the original query. Once the
index is proven, the negative proof could later read from it too; that is not
proposed here.

### Finding outside the ruling: filing-drift hint

On old specs with large trace footprints, the second positive-path cost is the
filing-drift hint (`filing_drift_hint_until`, `trace.rs:844-958`). It is called
serially after collection (`requirements_cli.rs:6332`) and costs 451-454 ms for
STORY-1889. The index cannot reach it. AC4 for STORY-1889-shaped specs needs a
separate decision, for example running the drift walk concurrently with the
shipped check and branch search, or bounding it tighter than its 1 s per call.
This sketch does not propose code for it. It is flagged so the AC4 measurement
does not come as a surprise.
