## 1. Overview & Lock Hierarchy

All mutations to the git-canonical requirements store (`<store>/objects/`, `<store>/metadata.yaml`, `<store>/oplog.yaml`, `<store>/registry/`, `<store>/claims/`, `<store>/locks/`, `<store>/schedule/`, `<store>/mailbox/`, `<store>/timing/`, and `<store>/regen/trials/`) serialize through the store write lock at `<store>/.aida/store-write.lock` (`STORE_WRITE_LOCK_FILE` in `aida-core/src/db/store_lock.rs:34`, acquired by `acquire` (`aida-core/src/db/store_lock.rs:135`) and `with_store_write_lock` (`aida-core/src/db/store_lock.rs:252`)).

### Canonical Lock Order (Binding Ruling A1)

When a store writer touches both the store repository and the shared ID block registry (`<store>/registry/blocks.yaml`, guarded by `<store>/registry/blocks.lock` via `with_dispense_lock` (`aida-core/src/node.rs:880`)), the mandatory lock acquisition order is:

1. **Outer**: `with_store_write_lock` (`aida-core/src/db/store_lock.rs:252`) (`<store>/.aida/store-write.lock`)
2. **Inner**: `with_dispense_lock` (`aida-core/src/node.rs:880`) (`<store>/registry/blocks.lock`)

Runtime enforcement in `acquire` (`aida-core/src/db/store_lock.rs:135`) checks `dispense_lock_held` (`aida-core/src/node.rs:827`) and refuses any non-reentrant `store-write.lock` acquisition while `blocks.lock` is already held on the current thread. Network `git fetch` / `pull_rebase` / `push_exact` operations never run while holding `blocks.lock`, and `push_exact_outcome` (`aida-core/src/git_ops.rs:1279`) asserts `!any_store_write_lock_held()` so network pushes always run outside `store-write.lock`.
