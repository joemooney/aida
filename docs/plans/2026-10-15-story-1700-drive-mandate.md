# STORY-1700: drive mandate (implementer sketch)

Status: SKETCH, awaiting advisor signoff. No product code yet.

STORY-1700 drive mandate (ADR-77), built on #2687 (STORY-1698) and STORY-1699
1. Record. Mandate gains `#[serde(default)] scopes: BTreeSet<Scope>` with Scope = ship-held | sketch-signoff | relay-restart | dispatch. `scope` stays "ship-held" on disk, so #2687 readers (load_all filters scope==ship-held) still see a drive mandate and keep honouring its ship part. Effective scopes = {scope} ∪ scopes; `--drive` writes all four plus kind="drive". CLI: `aida mandate start --drive [--ttl] [--reason] [--exclude-supervised]`. `--drive` implies --ship-held and sets include_supervised=true unless --exclude-supervised is passed. The rest of #2687 is unchanged: require_direct_human for start/stop, 24h max TTL, no extension, one active at a time, operator-only never covered. ship_decision is reused as is.
2. Display. New `aida mandate status --line` prints one line: "MANDATE drive · 5h40m left · by joe · reason · gates: none". SessionStart: aida-session-context.sh prints it for every seat, and relay sessions get it the same way because they fire SessionStart. Per turn: `aida awaiting --notice` (already run each turn by aida-mail-notice.sh, Claude and Codex) adds the line while the mandate is active, plus one line when it expires or is stopped. No new hook process. `aida session handoff --show`: compose_handoff_show takes an ACTIVE MANDATE block that prints before STANDING ORDERS. It is read live from ~/.aida/mandates at show time and never copied into handoff text, so a rotation cannot carry a stale or expired mandate.
3. Heartbeat. New substrate job `mandate-drive` (every 15m, `when = "mandate.drive_active == true"`, a new predicate flag field) runs `aida fleet drive --tick`. That command reuses STORY-1699's lane classifier and has no model and no seat grant. Per stalled or blocked lane it picks ONE action:
   - SUBSTRATE (runs in the tick): re-read state; expire leases on dead pids; nudge the PR's owner by mail. Restart a relay whose relay.status is exited/crashed and which has no .done marker, using its recorded launch (driver registry STORY-1653 + relay.status). This is allowed only if the grant it launched with is still valid and its principal == mandate.principal. The tick never mints or extends a grant (FAQ-42 floor). Otherwise it records "needs operator: grant expired".
   - SEAT (routed to the advisor as due items with the exact command): ship an APPROVED PR via `aida pr ship N`. The STORY-1698 gate needs an advisor grant and an anchored shipper, so a tick-run ship would fail with ShipperUnanchored, by design. Also: sketch signoff; re-dispatch a fixer for an approved, unowned spec or a dead lane (`aida agent new --bg`, which needs a model and a delegating grant); and a relay BLOCKED with exit 3 waiting on advisor signoff. For that relay the advisor resolves the cause, and the next tick does the restart as a substrate action.
   Due items go out as one MandateDriveDue event per (lane, action, head-sha), deduplicated across ticks. The seat job `mandate-drive-route` (seats=[advisor], on MandateDriveDue) surfaces them in `aida awaiting`. A lane that cannot be acted on records why (gated, operator-only, grant expired, floor).
4. Gates. Config `[mandate.human_gates] ops = []`, empty by default. ops ⊂ {ship, sketch-signoff, relay-restart, dispatch, hold-clear}, and an unknown op is a config-load error. A spec tagged operator-only or with execution_mode=Operator is always gated. The list is read from the main checkout's committed .aida/config.toml unioned with ~/.aida/config.toml. Layers can only add gates, so a branch cannot loosen them. A gated action becomes an operator notification plus a ledger "gated" row, and the lane keeps moving where it can.
5. No advisor. "Advisor live" means a valid advisor seat grant plus turn-clock activity within 30m. If that fails, the tick pushes ONE operator notification per absence episode (marker keyed by mandate id + episode start). It keeps doing substrate actions and leaves seat items queued for the next advisor, who sees them via awaiting and handoff --show.
6. Ledger. Every mandate-driven action emits MandateAction{mandate_id, actor: tick|session, lane, subject (PR/spec/run), action, outcome: done|routed|gated|refused|skipped, why} to .aida/events.jsonl. The tick run is also ledgered at aida-store schedule/mandate-drive.yaml (schedule_ledger). The STORY-1698 ship path emits MandateAction on both success and refusal. `aida mandate status` shows counts and the last 10 actions; `aida digest` and `aida fleet digest` get a "Mandate-driven" section.
7. Tests (story_1700_drive_mandate_tests.rs):
   - record round-trip: a #2687-shaped JSON still loads; a drive record loads in the #2687 loader as ship-held; include_supervised defaults on with --drive; start/stop refuse non-TTY.
   - --line, the notice line, and handoff --show ordering (mandate, then standing orders, then handoff).
   - fixture lanes for exited relay (valid grant → restart, expired grant → refusal recorded), blocked-exit-3 relay → routed, approved PR → routed ship, unowned approved spec → routed dispatch, operator-only → gated.
   - human_gates parsing: unknown op rejected, branch layer cannot remove a gate.
   - dedup of due items across two ticks; one operator escalation per absence episode; predicate field type-check; MandateAction emitted for every outcome.
Floors kept: attested independent review, no self-merge, no force-push or rewrite, mandate mint/stop human-only, tick never holds or mints a grant.
