## 0. The honest model — guardrail, not security

AIDA's store is a shared git branch: **anyone with push access to `aida-store` can edit any YAML directly.** Therefore RBAC here **cannot be a security boundary** — a determined user can always bypass the CLI with raw git. What it CAN be, and what's valuable for a team:

- **A guardrail** — the CLI refuses operations your role shouldn't do, preventing *accidents* (an implementer accidentally approving a spec, a teammate force-merging).
- **Encoded team structure** — the roster records who is advisor vs implementer, so tools, statuslines, and routing know.
- **An audit signal** — bypasses are visible in history (`author` + the git log), so the guardrail + the audit trail together deter misuse even though they don't prevent it.

This is the same trust model as the existing `AIDA_SESSION_ROLE` gating (which is self-declared per session); RBAC makes it **durable per-user** instead of per-session-env, so it survives a forgotten env var. We document the caveat loudly so no one mistakes it for access control.

## 1. What exists

- **Role gating today:** `AIDA_SESSION_ROLE` (advisor/implementer) is self-declared per shell; advisor-only ops (status transitions to approved/planned, queue grooming) check it. Per-session, not per-user — a user with no env set is "default" and ungated in some paths.
- **Roster:** STORY-640's `aida team` lists registered nodes/users from `registry/nodes.toml`.
- **Identity:** `current_user_id()` = `$USER`/`AIDA_USER` (the person, keyed independently of node/clone).

## 2. Design

### Storage — `registry/team.toml` on the store (keyed by USER, not node)
A person may have several clones/nodes, so role belongs to the **user id**, not a node:
```toml
[members]
alice = "advisor"
bob   = "implementer"
# absent user = unranked (falls back to AIDA_SESSION_ROLE / current behavior)
```
On the `aida-store` branch (shared, synced). One small file; CAS push-wins on concurrent edits (mirrors the registry pattern).

### Effective role resolution
`effective_role(current_user_id)` = roster role for the user, ELSE `AIDA_SESSION_ROLE`, ELSE unranked/default. So:
- A user in the roster gets their durable role regardless of env (the guardrail survives a forgotten `AIDA_SESSION_ROLE`).
- A user not in the roster = exactly today's behavior (backward-compatible).

### Enforcement
The operations already gated on advisor (find them: status transitions to approved/planned/rejected, `aida queue add`/grooming when role-gated, intake/assess) consult `effective_role` instead of only the session env. A non-advisor effective role → refuse with a clear message ("approving specs is an advisor action; your team role is implementer — ask an advisor, or `aida team set-role` if that's wrong"). `--force` / an env opt-out remains (it's a guardrail).

### Commands
- `aida team set-role <user> --role advisor|implementer|<role>` — write the roster role (CAS push). Self-service-ish (guardrail model: anyone can set, but it's audited).
- `aida team` (STORY-640) — show each member's role alongside host/last-seen.
- `aida team my-role` / surfaced in `aida status` + statusline.

### Backward-compat / safety
- No `registry/team.toml` / user absent = current behavior (env-based, ungated default). Old binaries ignore the file.
- Best-effort: store unreachable → fall back to session-env role, never block.
- The caveat (guardrail not security) is documented in `--help`, the command output, and `docs/`.

## 5. Open question: cross-machine person unification (STORY-653 follow-up, NOT solved)

STORY-653 made the dashboard team layer key on the **person identity** that
roles/queues/assignees use — the node owner `$USER` string (STORY-652's node
`user` field), falling back to the email local-part, then the integer `user_id`
for old nodes. This fixes the integer-vs-string mismatch (a role set in the UI is
now the key `effective_role` reads, so it actually enforces). But it leaves a
deeper identity question **deliberately unsolved**: the same human may register
under a *different* `$USER` on different machines (`joe@imac` vs
`joe.mooney@spock`) — and historically a shared integer `user_id` may have
*collapsed* two different people into one row. Deciding "who is one person across
accounts" is a separate design question (it needs a person↔account mapping, or
git-email/identity reconciliation, or an explicit `aida team link <a> <b>`), not
something string-keying can settle. The current behavior is the honest floor:
group by the owner string, show the email/node-name labels so a human can SEE the
split, and let the operator reconcile by setting a consistent `AIDA_USER` per
person. Tracked as a follow-up TASK. trace:STORY-653
