## 1. Antigravity Skill Registry and Plugin Surface

Unlike Claude Code (which uses markdown `SKILL.md` skills under `.claude/skills/` plus JS workflows) or Codex (which leverages `.codex/skills/` templates), Antigravity features a native **plugin/extension management subsystem** exposed via the `agy plugin` (alias `agy plugins`) command.

### A. The Plugin Command Interface
The `agy plugin` command surface provides the following management actions:
* `agy plugin list`: Lists all imported and active plugins.
* `agy plugin install <target>`: Installs a plugin directly, with support for registry references like `plugin@marketplace`.
* `agy plugin uninstall <name>`: Removes an installed plugin.
* `agy plugin enable/disable <name>`: Dynamically toggles plugin execution status in the runtime environment.
* `agy plugin validate [path]`: Validates plugin structure and manifest options before import/installation.
* `agy plugin link <mp> <target>`: Generates connection links to external extension marketplaces.

### B. The Cross-Platform Import Bridge: `agy plugin import [source]`
A key capability of the Antigravity plugin system is its ability to import and convert extensions from other major LLM platforms. Running `agy plugin import` searches for and imports plugins from:
* `gemini` (Google's native extension format)
* `claude` (Anthropic's Claude Code plugin format)

This import bridge allows Antigravity to reuse existing community plugins and tool definitions from the Claude Code ecosystem, translating them into its own internal tool-call schema.

## 2. Multi-Agent Capabilities: A Three-Way Comparison

## 3. How Antigravity Maps to AIDA's Multi-Agent Substrate

Because Antigravity lacks native background supervision and concurrent workflows, it relies on AIDA to wrap and manage its multi-agent behaviors:

1. **Worktree Isolation via Sibling Worktrees**
   * While Claude Code automatically checks out worktrees under `.claude/worktrees/` for background sessions, Antigravity executes inside sibling directories (e.g., `/home/joe/ai/aida-spike-28`) generated by `aida session start --owns <SPEC>`.
   * No `.aida-store` symlink is needed — a sibling worktree resolves the canonical store automatically via git's common-dir (BUG-331), so Antigravity interacts with AIDA's spec graph without per-worktree setup.

2. **Brief-Driven Task Arrival**
   * Antigravity discovers new work using AIDA's agent-brief channel. It calls `list_briefs({agent: "antigravity"})` over the MCP stdio interface, processes the markdown instructions in `/home/joe/ai/aida/.aida/agent-briefs/antigravity/`, and acknowledges them via `ack_brief`.

3. **Mailbox-Based Inter-Agent Communication**
   * To coordinate with Codex or Claude, Antigravity uses AIDA's messaging tools over the MCP bridge:
     * `send_message({to: "codex", body: "..."})`
     * `read_inbox()`
   * This abstracts message routing to AIDA's central coordination database rather than relying on a local socket daemon.

## 4. Refined AIDA Dispatch Policy for Multi-Agent Work

Based on these architectural findings, AIDA's dispatcher should treat Antigravity under the following policy:

1. **Abstract Worktree Isolation at the Substrate**
   * Do not expect Antigravity to handle multi-task concurrency or branch switching natively. AIDA must continue to enforce strict one-lease-per-worktree boundaries via `aida session start` before handing off execution to the `agy` binary.

2. **Leverage the Plugin Bridge for Custom Tool Injection**
   * To inject AIDA-specific developer skills (like `aida-pickup` or `aida-plan`) into Antigravity sessions, AIDA can package these skills as Claude-compatible plugin definitions and load them at launch using `agy plugin import claude` or local path installation.

3. **Enforce Heartbeat-Based Status Monitoring**
   * Since Antigravity does not have a native supervisor daemon to report process status, `aida status` must actively poll active PID logs under `.aida/agents/*.toml` and monitor busy/idle states based on MCP tool-call timestamps (`last_active_at`).
