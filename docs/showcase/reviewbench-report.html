Why ReviewBench §7.3 Stratifies Recall by Severity

HIGH HIGH-SEVERITY RECALL + LOW LOW-SEVERITY RECALL IS BY DESIGN

Methodology §7.3

ReviewBench’s methodology documentation (§7.3) explicitly notes:

“An agent designed to surface only the most impactful issues and to suppress noise should be evaluated on recall stratified by severity. High recall on severity = high paired with deliberately low recall on severity = low is a feature, not a failure; an unstratified recall number would penalize this agent unfairly.”

1. In Plain Terms: Why Does AIDA Rank So High on ReviewBench?

SOLVING THE TRADITIONAL PRECISION-VS-RECALL TRADE-OFF THROUGH SEPARATED FINDER / CHALLENGER SEATS & STRUCTURAL CONTEXT

100.0% Grounded Precision · 83.3% High-Severity Recall

Look at the published leaderboard above and a clear pattern emerges: most AI code reviewers are trapped in a single-pass compromise. Tools that prompt a model to be conservative (such as Copilot code review, Cursor, or Greptile) achieve high precision (95–98%) only by staying quiet—missing 40% to 80% of critical High-severity bugs (20–62% recall). Conversely, tools that prompt a model to be aggressive surface more bugs but flood the developer with speculative TOCTOU warnings, style nits, and unreachable edge cases. AIDA breaks that trade-off through four architectural choices:

A. Decoupled Red-Team Finder vs. Blue-Team Challenger

Instead of asking one prompt to simultaneously brainstorm bugs and self-censor, AIDA separates the cognitive roles. Pass-1 Finder is free to hunt aggressively across playbooks and security facets (surfacing 43 candidates across the 4 PRs). Pass-2 Challenger then acts as a skeptical senior maintainer, verifying each candidate against full file contents and dismissing 55.8% (24/43) unless it passes all three gates: Factually True + Change-Relevant + Actionable & Non-Trivial.

B. Full Target-File + CodeGraph AST Call-Graph Context

Diff-only reviewers miss bugs whose root cause sits 15 lines outside the diff hunk (like MinimizeCopilotComments() in gh-copilot-review#9) or in an untouched caller file (like tools.ts calling validatePattern() without flags in TechDebtMCP#135). And they emit false positives when a security invariant is already enforced earlier in the call chain (like base_dir 0700 permissions in chronicle#14). Injecting full target files + .codegraph/codegraph.db caller/callee edges gives both passes real structural visibility.

C. Stem-Coupled Batching & Polyglot Domain Playbooks

AIDA’s Rust engine groups implementation files with their matching test files (customRulesEngine.ts + customRulesEngine.test.ts) into the same token-budgeted batch and activates language- and path-specific playbooks (rust + conditional security_path_traversal and security_permissions facets). The reviewer sees the code and its test contract together.

D. Deterministic Rust Snippet Anchoring & Coverage Gate

LLMs frequently miscount line numbers in unified diffs. AIDA requires the reviewer to quote the verbatim existing_code snippet, then resolves exact 1-based line ranges deterministically in Rust (anchor_snippet_lines) while verifying 100% file coverage (verify_coverage) so no file in a multi-file PR is silently skipped.

CONTINUOUS LEARNING LOOP · v4 ENGINE REFINEMENTS (COMMIT 41a11958d87) → 100% HIGH-SEVERITY RECALL (7 / 7) & 2.1× PARALLEL SPEEDUP

Studying our single missed High-severity TP and multi-batch latency in the v3 baseline led to six general-purpose engine upgrades in v4: (1) Nearest Package-Manifest Context (attaching read-only pyproject.toml / package.json / Cargo.toml / go.mod / pom.xml), (2) CodeGraph Untouched Caller/Callee Body Slicing (35-line function body slices for the top 3 untouched AST edges), (3) Bounded Parallel Batch Execution (std::thread::scope up to 4 concurrent batches), (4) Cross-Batch Finding Consolidation, (5) Deterministic Omission/Doc Line-Anchor Fallback, and (6) Inner-Quote JSON Sanitization.
