THE GOVERNED SOFTWARE FACTORY

From a conversation to a maintainable system

AIDA connects the work people and agents do with the intent behind it. Start with a conversation, develop the system, and keep enough structured context for the next bounded change. You can remain involved throughout or delegate selected stages under the project's policy.

When many agents work in parallel, you will see operational terms in status views, logs and handoffs: lanes, worktrees, leases, lock files, delta reviews, ratchets, merge holds, merge trains, riders, bisect, post-train pulls, and the state enums that drive them. This guide walks through the six stages of that workflow in plain language so you do not need to be a Git or AIDA specialist to read what the system is doing.

The collaboration loop

  • Discuss the outcome. A person and coding agent explore the problem, constraints and alternatives. The person can develop, challenge and review the work throughout.
  • Capture agreed intent. The agent records each spec, its intent, verifiable acceptance criteria, and consequential architecture decisions (ADRs) in the project graph. Ask to inspect the record before implementation.
  • Own a bounded change. Each bounded change is assigned an execution mode, a role, and a session. Isolated worktrees give separate changes their own checkout; leases and queue state coordinate ownership.
  • Implement and validate. Build the agreed behavior inside a sandbox, link it to its specs and run the relevant checks. New discoveries can require revised intent or a separate decision.
  • Review independently. In the governed PR workflow, a separate reviewer performs an independent review of the current head commit and its evidence (using AIDA's deterministic & adversarial code review engine). The author's self-check is useful preparation and does not constitute independent approval.
  • Integrate under policy. The authorized landing path checks the applicable ledgers and gates. Integration can lead to another conversation; a merged change and a released milestone are separate steps.

These are stages in an operating model, not a promise that every project uses one autonomy mode. The configuration guide explains how execution mode, guidance and authority remain distinct. The graphic is explanatory, not a live dashboard.

Tracing one feature end-to-end (Steps 1 to 10)

To see how all the roles and terms fit together in practice, follow a single feature idea — *"Add jittered retry backoff to the webhook client"* — across the five swimlanes below:

  • Steps ①–② (You and the Advisor seat): You describe the webhook retry idea in plain English. The agent captures a Draft spec with explicit intent and acceptance criteria (for example, maximum retry count, exponential backoff formula, and error codes). In the advisor seat, you bless the spec (aida approve <spec> --mode drain), which checks the project graph to confirm no BlockedBy dependency is still unfinished.
  • Steps ③–④ (The Implementer lane): Running aida queue work allocates an isolated lane: AIDA creates a sibling Git worktree on disk, writes a session lease bound to the agent process, and starts the implementer inside a sandbox. Your main checkout stays completely untouched while the implementer writes the retry logic, runs unit tests, commits with a commit trailer, and opens a pull request (moving the spec to Done).
  • Steps ⑤–⑦ (Independent Review, Rework and Delta Review): Fast CI runs compilation and static ratchets while AIDA routes a review story to the reviewer seat. Suppose the independent reviewer spots a missing timeout check and records Changes Requested. AIDA places a rework merge hold and triggers a rework round (aida rework). The implementer pushes a follow-up commit, and the reviewer runs a targeted delta review of the new head commit, recording an Approved verdict that automatically releases the rework hold.
  • Steps ⑧–⑩ (Merge Train, Landing and Post-Train Pull): Now a main-track candidate, the pull request boards the merge train as a rider alongside other approved PRs. The train runs the seven-shard full CI tier (ci:full) once for the combined batch. When it finishes green, the batch lands on main, and your next post-train pull (aida pull) syncs the code and auto-bumps the spec to Completed.

Act 1: The workshop — queues, lanes, worktrees, leases and rotation

If two people or agents edit the same folder at the same time, they overwrite each other's files. AIDA prevents that by giving each active task its own isolated lane.

  • Backlog, grooming, batches, queues and pickability. Newly captured specs start in the backlog. An advisor runs aida groom (groom) to tighten acceptance criteria, assign an execution mode, optionally group related specs into a batch (batch:<name>), and route Approved specs into a role's queue. Running aida queue work (a launch) evaluates pickability across the project graph for blockers, verifies that the seat is free and within the host concurrency cap (cap), and spawns an agent process and AI model inside a sandbox (using auto mode or interactive guided mode according to the spec's execution mode and the session's autonomy mode).
  • Lane and Git worktree. Each launched task runs in its own lane backed by a dedicated Git worktree — a separate directory on disk checked out to that task's branch. Five implementer lanes can compile and run tests side by side without touching your main checkout.
  • Session, claim and lease. When a lane starts, AIDA moves the spec to InProgress and records a session, a claim on the spec or pull request, and an on-disk lease tied to the running process. The lease is an "occupied" sign: another session cannot pick up the same work while the lease is live.
  • Handoff and rotate. Long conversations eventually fill an AI model's context window. Before that happens, the session writes a handoff note summarizing what is done and what remains, and AIDA can rotate a fresh session into the seat without losing progress.
  • Orphaned leases, stale worktrees, GC and sweeps. If an agent process crashes or loses power without ending cleanly, its lease record is left behind as an orphaned lease and its folder becomes a stale worktree. AIDA refuses to silently overwrite uncommitted work; instead, the watchdog flags the dead session and a cleanup sweep or garbage collection pass (aida worktree gc, see GC) salvages any work and frees the branch.

Act 2: The control tower — seats, grants, mandates and deputies

In AIDA, wearing a role label shapes what you see, but taking a privileged step — approving a spec, recording a review verdict, clearing a hold, or merging to main — requires a live grant for that seat.

The four seats in the multi-seat workflow

Product seat (product — intake, ordering and launching work): The product seat owns requirement intake, acceptance criteria quality, backlog ordering, and launching eligible waves of work when the queue is ready and the drain lock is free. An operator or agent enters the seat with eval "$(aida role enter product)" (or spawns a session with aida agent new <vendor> --role product), files and refines specs with aida add and aida edit, inspects the queue and active fleet with aida queue list, aida ps and aida schedule due --seat product, and launches implementation waves with aida queue work <spec> --role implementer --no-human or aida agent new <vendor> --role implementer --spec <spec>. To prevent the author of a product direction from silently becoming its approver, the product seat never crosses disposition gates (aida approve), never approves its own disputed judgment, and never merges implementation code.

Advisor seat (advisor — independent disposition, review and merge readiness): The advisor seat owns the judgment gates: spec disposition, ruling on design-fork punts, judging rework round sufficiency, performing or routing independent review, and verifying merge readiness. Entered at a terminal via eval "$(aida role enter advisor --delegate-seat implementer)", the advisor inspects its actionable worklist with aida advisor and aida schedule due --seat advisor, blesses specs and sets their execution mode (aida edit <spec> --status approved / aida approve), records commit-pinned review verdicts with aida review record --verdict approved --sha <sha> --pr <n> <spec>, and ships reviewed changes under a human-minted terminal mandate (aida mandate start --ship-held --ttl 8h --reason "…", or aida mandate start --drive) or submits host/TTY scripts through the script deputy (aida deputy shell submit --file <script> --wait). The advisor never writes implementation code that it will later gate and cannot approve a pull request if its session or grant appears in the change's authorship ledger.

Integration seat (integration / integrator — promotions and merge trains): The integration seat owns the mechanical merge cascade: staging and landing integration branch promotions and batch merge trains onto main. Launched with aida agent new <vendor> --role implementer --seat integration (or entered via eval "$(aida role enter integrator)"), it checks which open pull requests are eligible to ride right now with aida pr train --check --all-open, previews train plans with aida pr train --dry-run, lands approved batches with aida pr train <n…> --max 10 or aida pr train --all-ready (and single PRs or verified slice stacks with aida pr ship <n> / aida pr ship <n> --rebase --final-slice), and syncs the repository afterwards with aida pull. Because the integration seat is strictly mechanical, it resolves only deterministic conflicts (formatting, import unions, lockfiles) and escalates any semantic conflict, failing test, or missing verdict through aida mailbox send --to seat:advisor "…".

Implementer lanes (implementer — isolated coding under any vendor): An implementer lane executes one bounded spec inside an isolated Git worktree and sandbox using whichever vendor CLI the project or invocation selects (claude, codex, or agy). Started via aida queue work <spec> --role implementer --vendor <vendor> --no-human (or aida worktree add <spec> --role implementer for background sessions, or aida queue work <spec> --auto-complete), the implementer writes code and targeted tests, runs make check-ci-fast, escalates unstated design choices with aida punt, writes a session handoff when rotating (aida session handoff --write <file>), and finishes its branch slice with aida queue done — holding a leaf child grant that can never self-approve or merge.

Vendor neutrality: coordination through aida mailbox and standing orders

AIDA's multi-seat loop is vendor-neutral: the same workflow runs whether a seat is hosted by Claude Code (claude), Codex CLI (codex), or Antigravity (agy). Rather than relying on vendor-specific chat primitives (such as Claude Code's in-memory SendMessage, which leaves no repository audit trail and never reaches a Codex or Antigravity seat), every cross-seat handoff, promotion notice, and escalation travels through the persistent mailbox (aida mailbox):

# Integration seat notifies whoever currently holds the advisor seat
aida mailbox send --to seat:advisor --intent fyi "Promotion landed on main; run aida pull"

# Advisor reaches the active integration seat or replies across session rotations
aida mailbox send --to seat:integration --intent request "Check train eligibility for open PRs"
aida mailbox send --in-reply-to <message-id> "Confirmed; train is green and ready"

# Read pending messages and commit the local mailbox digest to aida-store
aida mailbox inbox
aida mailbox sync

Addressing --to seat:advisor or --to seat:integration routes to whichever live session currently occupies that seat, and --in-reply-to <id> routes back to the sender's seat and role even if the sender rotated into a fresh conversation. Durable per-seat operating rules live in .aida/standing-orders/<seat>.md, managed via aida session handoff --seat advisor --standing-orders add "<text>" and printed automatically at session start alongside the latest handoff via aida session handoff --seat <seat> --show. Act 3: The inspection gates — reviews, delta reviews, CI tiers, ratchets and holds

Once an implementer finishes coding, it creates a Git commit with a commit trailer (or intermediate Refs trailer) naming the spec and opens a pull request (PR on GitHub, MR on GitLab). Before that change becomes a main-track candidate, it must pass three independent gates backed by local and store ledgers.

  • Gate 1 — Independent review, head pinning, rework and delta review. A reviewer in a separate seat performs an independent review of the pull request against the spec's intent and acceptance criteria. The verdict is pinned to the pull request's exact head commit SHA in the review-verdict ledger. If the reviewer requests changes, the spec enters a rework round: an implementer pushes a fix commit to the same pull request, and the next reviewer pass can run a delta review focused on the new commits since the prior verdict.
  • Gate 2 — Two-tier CI, pinned CI workflows, informational vs required checks, ratchets and lock tests. Continuous Integration (CI) runs automated jobs defined in the repository's CI workflow files (.github/workflows/*.yml or .gitlab-ci.yml, whose content digest is pinned for freshness so stale workflow definitions are refused) and reports green or red. Checks split into two classes:

- Required checks vs informational CI workflows (allowed failures): Secondary advisory pipelines — such as Build (windows-latest) or Build (macos-latest) in a Cross-platform workflow, an external mirror check (ci/gitlab-mirror), or nightly benchmark suites — can be configured in .aida/config.toml under [ci] informational_workflows (default: ["Cross-platform*"]) or informational_checks (default: []) using * wildcards. When an informational check is pending or fails, it is reported as an allowed failure and does not delay aida pr ship. As a hard-coded safety floor, any check listed as required in forge branch protection (and AIDA's primary Build (ubuntu-latest) gate) always overrides the informational allow-list. - Fast CI tier vs full CI tier (ci:full): Ordinary pull requests run the fast tier by default: workspace compilation, documentation guards, and ratchets — rules that tolerate a recorded legacy baseline (such as warning counts or portability exceptions) but fail if a change introduces any new violation. Adding the ci:full label (or AIDA_PR_CI_TIER=full) or boarding a merge train runs all seven test shards, including lock tests that stress concurrent store and seat locking. Direct aida pr ship requires the full CI tier; fast-tier PRs land via the merge train.

  • Gate 3 — Merge hold and clear (when, by whom, and why holds arise). A merge hold (often shortened to hold) is an explicit stop sign (aida:merge-hold label + merge-hold-gate check) that blocks a pull request even when review and CI are green. Holds arise from five explicit triggers (HoldReasonKind, ordered by strictness Recusal > Decision > Rework > Supervision):

- Supervision (placed automatically by AIDA on PR open/update): when a PR implements a spec in drive or guided mode, a supervised spec (keystone), or modifies protected gate/workflow paths (GATE_PROTECTED_PATHS or [mandate.human_gates]), so high-consequence work pauses for human sign-off. - Rework (placed automatically by AIDA on review refusal): when an independent reviewer records Changes Requested, preventing unresolved review findings from merging. - Decision (placed automatically on a punt or manually via aida pr hold <pr> --reason "…"): when an unstated product choice or an operator freeze blocks the PR. - Recusal (placed automatically by AIDA on conflict of interest): when the advisor or principal who touched the branch would otherwise be in the path to approve or ship their own work (or no independent reviewer reader is available). - Failed mandate re-arm (restored automatically by AIDA): when an unattended mandate ship preflight fails mid-flight, restoring the hold so the PR never stays unheld by mistake. - Who may clear each hold: a rework-only hold (Rework with no stricter reason composed) clears automatically when a granted reviewer approves the new head SHA; a Supervision hold clears via aida merge-hold clear <pr> at a human terminal or via an active --ship-held mandate; Decision and Recusal holds are hard-coded to require a non-recused human at a terminal.

Act 4: Landing paths — direct ship, merge trains, bisect and integration promotion

In the multi-seat workflow, work advances through a strict five-stage landing sequence: implementer lane pull request → full CI tier green → independent review → merge train (or integration promotion) → main.

  • Why review requires green CI and why a train requires full-tier CI at the exact approved head: An implementer's pull-request description is an assertion, not evidence. Requiring CI to be green before a review is finalized ensures reviewers never waste cycles reading code that fails compilation, static ratchets, or regression tests, and ensures any fix commit pushed to repair a failing check is reviewed at the new head commit SHA. On repositories with tiered CI, recording an independent approval (aida review record --verdict approved --sha <sha> --pr <n> <spec>) triggers the seven-shard full CI tier (ci:full) on that exact head commit, and aida pr train admits a pull request only when its exact approved head SHA already has a green full-tier CI run (unless explicitly overridden with --skip-full-check, which is logged to the activity audit trail). If a branch head moves after approval, or if two individually green pull requests interact semantically when combined, an older CI result no longer proves the landing tree is healthy — which is why the train both requires green full-tier CI at each member's approved head and re-runs full CI on the combined train/* stack before merging pinned to that tip (--match-head-commit <tip>).
  • Path A — Direct ship (aida pr ship <n>). For a single pull request whose current head is up to date with main and has already passed an independent review and the full CI tier (ci:full), aida pr ship <n> verifies the ledgers and gates, acquires the merge lock, and squash-merges (or rebase-merges verified mechanical slice stacks via aida pr ship <n> --rebase --final-slice) onto main. If the PR's head is behind main, aida pr ship refuses and points to aida pr train <n>.
  • Path B — The merge train (aida pr train <n…> / aida pr train --all-ready). Two pull requests that are each green in isolation can still break main together when neither PR's CI saw the other's changes. The integration or advisor seat checks candidate readiness with aida pr train --check --all-open (or previews with aida pr train --dry-run) and batches up to --max 10 approved riders onto a single train/* pull request:

- Admission and patch-id carry-over: Each member must pass the same gates as aida pr ship (open, non-draft, targeting the default branch, no active merge hold, approved at its current head or carried over a clean merge from main, and holding a green full-tier CI run at that head). The train stacks main plus one squash commit per member and verifies that each stacked commit's git patch-id matches the member's approved diff (merge-base(main, head)..head); any conflicting or altered member is dropped with its reason so you never hit a wrong PR admitted hazard. - Green train on an unmoved main: Required checks run on the exact combined train/* tree main will receive. When ci:full finishes green and main has not moved under the merge lease, the train rebase-merges pinned to the tested tip (--match-head-commit <tip>), closes each member PR with a pointer to its landed commit, and runs aida pull. - Red train and automatic bisect: If a test fails on the combined train (red), AIDA never blindly reruns the failing batch (only a run cancelled before producing a test result is retried once). Instead, it splits the riders in halves (bisect), two sub-trains at a time: any green half lands immediately, and the failing half is rebuilt on the new main until the single offending blocker PR is isolated and left open with a diagnostic comment.

  • Path C — Integration track and promotion. When several specs build a coupled subsystem or milestone together, implementer lanes target a shared integration branch track (--base <branch>). The integration seat merges verified slices onto the integration branch, runs full gate verification, obtains an independent delta review from the advisor seat against the prior promotion head, and lands the batch onto main in a single promotion pull request.

Recurring duties as aida schedule jobs: the guard → route pattern

Rather than burning model tokens in in-session polling loops, aida init seeds a repository-owned job registry (.aida-store/schedule/*.yaml, inspected with aida schedule status and driven every 15 minutes by aida schedule tick via aida schedule install-cron or aida schedule install-systemd). Scheduled jobs follow a two-tier guard → route architecture:

1. Deterministic substrate guard jobs (Kind = substrate, Seats = *) run lightweight aida doctor check … --fail-on-findings or maintenance commands on a fixed cadence (every 15m, every 30m, every 1h) with zero LLM token cost while healthy. 2. Event-driven seat route jobs (Kind = seat, Seats = advisor, Schedule = on CronJobFailed:<guard>) stay dormant until their paired substrate guard exits non-zero. When a guard trips, aida schedule tick attaches the trip evidence and marks the -route job due for whichever session holds the target seat (aida schedule due --seat advisor), which acts on the finding and clears the duty with aida schedule done <job>.

Where the multi-seat factory is heading: aspirational & next-horizon capabilities

While aida init today ships the four-seat role model, commit-pinned review and train gates, aida mailbox, and the guard → route schedule registry above, several next-horizon capabilities are planned to close the remaining gap between operator habits and a fully self-governing dark factory:

  • 1. Proactive landing-health guard & shared-failure diagnosis (planned): Today, if a CI step timeout or base-branch regression turns several open pull requests red at once, seats sweeping individual PRs can see "no merges" without immediately recognizing the shared root cause, and an integration seat waiting on long remote gate checks can look indistinguishable from an idle session. The planned landing-health-guard (aida doctor check landing-health --fail-on-findings paired with landing-health-guard-route to the advisor and product seats) alerts when main has not moved beyond landing_gap_minutes (default 90 minutes) while open PRs exist, correlates identical failing CI steps across 3 or more open PRs as a probable shared infrastructure or base cause, monitors CI step duration headroom (warning when recent passes exceed 80% of timeout-minutes before the step turns red), and surfaces each seat's declared wait state (what it waits on, since when, and expected completion).
  • 2. Head-pin lock on approved and train-pinned pull requests (planned): Moving the branch head of a pull request that already holds an attested approval at its current head or is pinned to an active merge train invalidates the approval and forces re-review. A planned head-movement guard refuses branch-advancing commands (aida pr rebase, aida pr update, rework publish) whenever the PR is approved at its current head or pinned by a live train unless a human explicitly passes --force-unpin, while invalidating approvals and posting a notice if a raw git push bypasses the CLI — paired with sub-10-second cached aida pr state and aida pr list views showing approval heads, train pins, and holds at a glance.
  • 3. Pipelined integration promotions (integration.pipeline_depth, planned): Today, while promotion *N* waits on full CI or the advisor's delta review, the integration seat waits serially before assembling promotion *N+1*. A planned integration.pipeline_depth project knob (default 0, settable to 1) allows the integration seat to assemble and gate promotion *N+1* on a staging branch atop promotion *N*'s head from PRs already approved for the integration track — running gate checks only when build-host slots are free beyond active implementer lanes, and merging *N*'s reworked head into *N+1* if *N* changes — so *N+1* is ready to open the instant *N* lands.
  • 4. First-class product standing orders, scheduled landing sweeps & declarative fleet policy (planned): Standing orders exist in the template master for the advisor and integration seats, while product-seat standing orders, periodic landing sweeps, and fleet sizing heuristics (such as capping concurrent implementer lanes at 4 and reviewers at 2, routing only conflict or architecture-design work to top-tier reasoning models, and automatically re-scoping a spec at rework round 3) still live in operator handoff notes or session-local crons. Promoting these into template standing orders, default aida schedule seat jobs, and .aida/config.toml fleet policy knobs ensures a newly initialized repository inherits the full cadence under any vendor.
  • 5. Native remote build-host lane execution (planned): High-concurrency operators today offload headless implementer lanes and heavy cargo test runs to a dedicated Linux build server over SSH using custom shell scripts (documented in operator setup). A planned native remote-lane host driver brings SSH lane provisioning, seat snapshots, and remote store sync directly into aida queue work and aida lane job.

Act 5: After landing — post-train pulls, store sync and stale pull recovery

Landing code on the remote main branch is not the final step; local checkouts, telemetry, and the requirement store must stay in sync with what just landed.

  • Auto-bump from Done to Completed (vs Refs). As soon as a commit carrying a completion commit trailer ((<spec-id>)) lands on main, AIDA's auto-bump reconciles the spec's state from Done (finished on a branch) to Completed (merged on main). Intermediate commits or unfinished aida ship preflights use a non-closing Refs trailer ((Refs <spec-id>)) so progress is linked without prematurely closing the spec.
  • Post-train pull via private fetch refs (aida pull). After a train or promotion lands, local clones are behind the remote tip — a condition called a stale pull. Running a post-train pull (aida pull) fetches the remote branch into an invocation-private ref (fetch ref, leaving shared FETCH_HEAD untouched), acquires the store writer lock file, rebases or fast-forwards both the code checkout and the .aida-store/ worktree, and refreshes the local read cache.
  • Pull fixes, handle-pinned reads and telemetry. If an interrupted Git command left a stray lock file or uncommitted store state that blocks aida pull, applying a pull fix clears the obstruction safely. Every gate and status reader pins verdict and ledger files through a verified operating-system file handle (O_NOFOLLOW), and local telemetry records model provenance, effort calibration, and regeneration scores for aida metrics and aida digest.

When work takes a detour: the four recovery flowcharts

Real engineering rarely travels in a straight line. What makes a governed factory trustworthy is how it behaves when something goes wrong: an unstated product choice, a failed review, a broken test on a shared merge train, or a crashed terminal. Instead of guessing silently or corrupting your checkout, AIDA routes each detour through an explicit recovery loop.

  • Detour A — The agent hits an unstated choice (aida punt → NeedsAttention). If an autonomous implementer discovers two valid designs that the spec's acceptance criteria did not decide between, it refuses to guess. It calls aida punt --category design-fork, recording the question and its optional lean in the punt ledger and parking the spec in NeedsAttention. The rest of the batch drain continues past the parked spec; when you return, you answer the question with aida decide or aida clarify and resume from the exact checkpoint (aida queue work <spec> --resume).
  • Detour B — The reviewer requests changes (aida rework → Delta review). When an independent review records Changes Requested, AIDA places a rework merge hold on the pull request so it cannot accidentally ship. Running aida rework <spec> hands the reviewer's structured findings back to the implementer branch; once the fix commit is pushed, a delta review verifies the new head commit and automatically releases the rework-only hold.
  • Detour C — A merge train turns red (automatic bisect). When four riders board a merge train together and a test fails in the full CI tier (red), AIDA retires the failed train job and automatically bisects the batch into smaller halves ([R1, R2] and [R3, R4]). The healthy riders still land on main, while the single broken rider is isolated as a blocker for rework.
  • Detour D — A session crashes or a clone falls behind (Watchdog → Sweep & Pull fix). If a terminal closes or an agent process dies mid-run, the watchdog detects that the recorded <pid>@<starttime> is gone and marks the session's lock as an orphaned lease and its checkout as a stale worktree. A cleanup sweep (aida worktree gc) preserves any uncommitted work while reclaiming clean checkouts, and aida pull (or a pull fix if a stray Git lock file remained) brings local checkouts back in sync with main.

Four records with different jobs

  • Code history: source, tests, trace comments and commits live on the product's code branches. Traces connect implementation to structured intent; they do not themselves approve a change.
  • Canonical intent (git canonical): the default git-canonical store uses the orphan aida-store branch (ref) and a live .aida-store/ worktree. YAML spec objects contain requirements, project graph relationships, comments and transition history. Store history is separate from code history and must be synchronized deliberately.
  • Derived read cache: .aida/cache-db/cache.db indexes store data in SQLite WAL mode for fast, lock-free reads. It checks freshness against the store HEAD, is rebuildable from the canonical store at any time, and is never consulted for authority decisions.
  • Local operational evidence: session leases, review-verdict ledgers, holds, telemetry and handoff notes have local runtime locations under .aida/; machine grants and mandates have their own local authority context under ~/.aida/.

User perspective: what you control, what you configure, and what is automatic

You do not need to memorize every internal term to use AIDA productively. From a user's perspective, AIDA's vocabulary falls into three distinct buckets:

Configurable project & host policies — settings in .aida/config.toml or ~/.aida/host.toml that tune concurrency, models, sandboxes, and informational CI allow-lists, with safe defaults out of the box. 3.
